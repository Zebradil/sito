sito and ncro both proxy Nix binary caches (Nix's downloadable build caches), but they aim at different machines. sito is a small routing daemon for a laptop that moves between networks. ncro is a bigger routing layer for a server or fleet: it stores routing decisions on disk, checks signatures itself and can share routes between machines. I compared sito's `main` against ncro's latest commit (`bb4fb83`), reading ncro's README, architecture doc and router source.

## Where they differ in design

- **Fanning out to every cache.** On every narinfo miss, ncro sends a request to cache.nixos.org and every other healthy upstream at the same time. sito's ADR-0003 rejects that as rude to public caches. ncro limits it with concurrency caps and a memory of recent misses, but still sends the requests.
- **Stale answers.** ncro keeps narinfo bodies for up to an hour, which is the second cache layer sito's ADR-0002 rejects. On the other hand, because the body is cached, ncro's "warm" requests never touch the network. That is where its advertised speed-up comes from. I haven't checked their benchmark.
- **Where trust lives.** ncro sits inside the trust chain: it verifies and rewrites narinfos. Nix still checks the signature, since the `URL:` line is not part of what is signed (that's from Nix's signing format, not checked in this code). But a compromised ncro can point downloads at a NAR of its choosing; Nix's hash check should still reject a wrong one, which I didn't verify. sito can only delay or deny a download.
- **Roaming.** ncro assumes the network doesn't change: it probes every 30s, keeps routes for an hour, and keeps routes across restarts. After a laptop wakes on a new network, it could keep sending requests to the LAN box until those routes are rejected. That is inference from reading the code; I didn't test it. sito's short probe interval, immediate re-probe on failure and cold start are built for exactly this case.

## Worth borrowing for sito

1. **Provenance header** (`X-Sito-Upstream`): a few lines, and it makes debugging easier without turning on debug logs. It overlaps with the "per-request info log" item in `todo.md`.
2. **netrc**: ncro depends on the `rust-netrc` crate, which confirms the ADR-0008 approach. If you need auth, reuse that crate rather than writing a parser.
3. **NAR hedging**: only useful if a slow first byte actually shows up in practice. Don't add it before then.

I'd skip SQLite, gossip between nodes, mDNS, path filters and rewriting narinfos. Each one works against an ADR you already accepted.
